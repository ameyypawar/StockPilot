# Progressive Web App — StockPilot (Inventory Management System)

Phase 3 of the project turns the ASP.NET Core MVC web app into an
installable, offline-capable Progressive Web App (PWA), layered on top of
the same MVC pages — no separate front-end framework.

## Where the PWA code lives

| Piece | File |
|---|---|
| App manifest | `ASPNETApplication/wwwroot/manifest.json` |
| Service worker | `ASPNETApplication/wwwroot/sw.js` |
| Offline fallback page | `ASPNETApplication/wwwroot/offline.html` |
| Install/offline-banner/notification glue | `ASPNETApplication/wwwroot/js/pwa.js` |
| Per-page PWA behaviour (search, stock, low stock) | `ASPNETApplication/wwwroot/js/pwa-pages.js` |
| Icons (192/512/maskable/apple-touch) | `ASPNETApplication/wwwroot/icons/` (generated by `tools/generate_icons.py`) |
| Mobile-first pages | `ASPNETApplication/Views/Pwa/{Index,Search,Stock,LowStock}.cshtml` |
| Page controller | `ASPNETApplication/Controllers/PwaController.cs` |
| JSON data API the pages call | `ASPNETApplication/Controllers/Api/InventoryApiController.cs` (`GET /api/products`, `GET /api/stock`, `GET /api/stock/low`) |
| Manifest/theme links, install button | `ASPNETApplication/Views/Shared/_Layout.cshtml`, `_NavLinks.cshtml` |

## How it works

### Manifest

`manifest.json` declares the app identity: `id: "/"`, name **Inventory
Management System** (short name `InventoryMS`), `start_url: "/Pwa"`,
`scope: "/"`, `display: "standalone"`, theme colour `#1E293B` (dark slate),
background colour `#F8FAFC`. It lists the 192px/512px icons plus a maskable
512px icon (20% safe-zone padding, so Android's circular/rounded-square mask
doesn't clip the logo), and two `shortcuts`: **Product Search**
(`/Pwa/Search`) and **Low Stock** (`/Pwa/LowStock`), which show up on a
long-press of the installed app icon.

### Three caching strategies (`sw.js`)

The service worker keeps three caches — `ims-static-v1` (CSS/JS/lib/icons),
`ims-pages-v1` (HTML page shells) and `ims-data-v1` (API JSON) — and applies
a different strategy per request type:

1. **`/api/*` calls — network-first, data cache.** Try the network; on
   success, store the response in `ims-data-v1` and return it. On failure,
   fall back to the last cached copy, adding an `X-IMS-Cache: hit` header so
   the page can show "offline – saved data".
2. **Page navigations — network-first, pages cache.** Try the network (skips
   `/Account/*`, since caching the login page is pointless and could leak a
   stale auth state); on success cache the page; on failure, serve the
   cached copy of that page, and if there isn't one, serve `/offline.html`.
3. **Static assets — stale-while-revalidate.** `css/`, `js/`, `lib/`,
   `icons/`, the favicon and the manifest are served instantly from cache
   while a background fetch refreshes the cache for next time. Lookups
   ignore the query string (`ignoreSearch: true`) because Razor's
   `asp-append-version` appends a `?v=` cache-buster to asset URLs.

Only successful, non-redirected, same-origin (`res.type === 'basic'`)
responses are ever cached. On install, the worker precaches `/offline.html`,
the manifest, the CSS/JS bundles (including Bootstrap and jQuery) and the
icon set, then calls `skipWaiting()`. On activate, it deletes any cache not
in the current set and calls `clients.claim()`.

### Offline data

`js/pwa-pages.js` drives the three PWA pages entirely from
`/api/products`, `/api/stock` and `/api/stock/low`, rendered with
`textContent` (never raw HTML, to avoid injection from stored data):

- **Search** (`/Pwa/Search`) filters products by name/category/supplier on
  every keystroke, client-side — so it keeps working from the cached JSON
  even with no connection.
- **Stock** (`/Pwa/Stock`) shows status-chip totals (Total/OK/Low/Out) and a
  status filter.
- **Low Stock** (`/Pwa/LowStock`) lists items at/under their reorder level
  with an on-demand "Notify me now" button.

Each page's `#dataStatus` line shows "Last updated {generatedAt}" and, when
the JSON came from the service worker's cache rather than the network, an
"Offline – saved data" badge. If neither the network nor the cache has data
yet, the page asks the user to "Open this page once while online to save
data."

### Notifications and background reminders

`js/pwa.js` exposes `window.IMS`. `#enableAlertsBtn` requests notification
permission, then calls `IMS.checkLowStock(true)`. `checkLowStock` fetches
`/api/stock/low`, builds a signature from the sorted `id:qty` pairs, and —
if the signature changed (or a check was forced) — calls
`registration.showNotification('Low stock alert', …)` with a link back to
`/Pwa/LowStock`. This runs once on page load and then every 15 minutes while
a tab is open; where the browser supports it, enabling alerts also registers
a `periodicsync` (`ims-low-stock`, minimum interval 12 hours) so the check
can also fire in the background on an installed, Chromium-based app.
`notificationclick` focuses an existing tab if one is open, otherwise opens
`/Pwa/LowStock`.

An offline/online listener toggles a visible `#offlineBanner`, and form
submits are blocked (with a banner message) while offline, since a POST
made offline would otherwise fail silently.

### Logout hygiene

Because the service worker caches pages that require a login, `Account/Login`
(reached with `?loggedOut=1`) posts `{ type: 'CLEAR_USER_DATA' }` to the
service worker, which deletes the pages and data caches, and clears the
`ims:lowSig` key from `localStorage`. Sessions are in-memory server-side, so
restarting the app also logs everyone out.

## Testing the PWA

### Desktop (fastest)

1. Run the app and open `http://localhost:5080` in Chrome.
2. Log in (`admin` / `Admin@123`), then open DevTools → **Application** tab
   → **Service Workers**, confirm one is activated for `sw.js`.
3. Still in DevTools → **Application** → **Manifest**, confirm the manifest
   loads with no errors and the icons render.
4. Tick **Offline** (Network conditions or the Application → Service
   Workers panel), then reload `/Pwa/Search` — it should still load and
   show the cached product list.

### Android phone

Run the web app on a profile reachable from the phone's Wi-Fi
(`LAN` for LocalDB, or `MacDockerLAN` for the Docker SQL setup — both bind
to `0.0.0.0:5080`), then get the phone to treat it as a secure origin one of
two ways:

- **(A) Chrome flag (simplest):** on the phone, go to
  `chrome://flags/#unsafely-treat-insecure-origin-as-secure`, add
  `http://<laptop-ip>:5080`, relaunch Chrome.
- **(B) USB debugging + port forwarding:** connect the phone by USB, enable
  USB debugging, then on the laptop open `chrome://inspect`, set up port
  forwarding `5080 → localhost:5080`, and browse to
  `http://localhost:5080` on the phone.

Either way, once the site loads: Chrome menu → **Install app** (or **Add to
Home screen**).

### iPhone

Safari on iOS needs a real HTTPS origin for a PWA — a plain `http://<ip>`
LAN address won't do. Put a tunnel in front of the app (e.g. `cloudflared` or
`ngrok`) so it's served over HTTPS, then: Share sheet → **Add to Home
Screen**. Push notifications additionally need iOS 16.4+ and the app to be
installed (not just open in Safari).

## Limitations

- Periodic background sync (`periodicsync`) is best-effort and
  Chromium-only, and only fires for an installed app — it is not guaranteed
  to run on a fixed schedule.
- Notifications require the user to grant permission, and on iOS require
  installation first; these can't be fully verified with `curl` and are
  called out as **manual** checks rather than claimed as automated ones.
- Sessions are server-side and in-memory, so an app restart logs every user
  out even if their browser still shows cached pages.
- A secure context (HTTPS, or `localhost`) is required for the service
  worker and installability — plain `http://<LAN-ip>` needs one of the
  workarounds above.
